# 项目协作规范

第一，生成或修改的代码必须写入简洁的英文注释；至少说明每个函数的作用、输入和输出，已有中文内容不能写成乱码。

第二，写完代码后，如果当前环境具备可测条件，需要直接验证代码链路是否能稳定运行，并在结果中说明执行过的测试命令和结论。

第三，如果测试过程中生成了临时测试文件、临时日志或一次性脚本，测试结束后需要删除；确需保留时，要说明保留原因和文件位置。

第四，修改代码前后都要做好版本管理；在进行比较大的改动时，如有必要可以开启分支；完成一组可验证的功能或修复并通过必要检查后，要主动进行阶段性 git 提交保存，不必等用户反复提醒；提交、存档和版本说明必须使用中文详细记录，提交前先检查工作区状态，避免混入无关改动。没有允许的条件下，不允许随便将改动推送到远程。

第五，保持良好的文件管理习惯；新增文件要放在职责明确的位置，命名清晰，尽量不要生成一千行以上的大文件。

第六，客观评价需求和方案；如果有成熟、稳定、符合当前技术栈的库或框架，并且需求确实需要，应优先询问是否要采用成熟方案。

第七，编辑代码时尽量避免写入大段体积的代码块，可以分段编辑写入

第八，在本次计划方案结束后，要实施更新根目录的README.md文档，详细记录目前的项目现状

第九，在制定计划时，如果有无法决定的决策，应该主动询问用户的意见，并且要给出你对这个决策的建议意见
