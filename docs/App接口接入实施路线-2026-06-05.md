# App 接口接入实施路线（2026-06-05）

## 背景

后端服务器地址：

```text
http://120.79.130.49:8790
```

当前仓库里有三类前端相关工程：

- `agentHubApp`：Expo / React Native 移动端，目前主要读取 `src/data/mockData.ts`。
- `agentHubFrontend`：Vite / React Web 端，已经有完整业务后端 API 封装 `src/api/businessBackend.ts`，但默认同源 `/api`，依赖 Vite proxy。
- `agentHubBackend`：业务后端，默认端口 `8790`，接口文档在 `docs/业务后端接口文档.md`。

本路线聚焦把 `agentHubApp` 从 mock 数据切到真实业务后端，同时保留 Web 端已有能力作为类型和交互参考。

## 已有接口能力地图

### 通用和工作台

- `GET /api/health`：健康检查。
- `GET /api/workbench`：工作区列表聚合，支持分页、搜索、归档筛选、排序。
- `GET /api/workspaces/:workspaceId/zip`：下载 Runtime workspace zip。

移动端首页、工作区切换、搜索、置顶/归档列表优先接 `GET /api/workbench`，不要再从旧的项目/会话拆分接口拼数据。

### 项目和工作区

- `POST /api/projects`：创建项目并创建或绑定 Runtime workspace。
- `GET /api/projects`：返回所有项目元数据。
- `GET /api/projects/:projectId`：单项目元数据。
- `PATCH /api/projects/:projectId/metadata`：批量更新置顶、归档。
- `PUT /api/projects/:projectId/pin`、`DELETE /api/projects/:projectId/pin`：置顶/取消置顶。
- `PUT /api/projects/:projectId/archive`、`DELETE /api/projects/:projectId/archive`：归档/取消归档。

移动端新建工作区应使用 `POST /api/projects`；切换、置顶、归档应使用 `GET /api/workbench` + metadata 更新。

### 项目运行态、聊天和事件

- `GET /api/projects/:projectId/state?messageLimit=40`：单项目聚合状态，包含 workspace、conversation、messages、agents、artifacts、workflowEvents 等。
- `POST /api/projects/:projectId/messages/stream`：发送消息并返回 SSE。
- `PUT /api/projects/:projectId/messages/:messageId/pin`：pin 消息到长期上下文。
- `DELETE /api/projects/:projectId/messages/:messageId/pin`：取消消息 pin。

移动端对话页优先接 `state` 和 `messages/stream`。当前没有单独的会话列表、消息历史、事件历史接口，不要依赖旧规划接口。

### Agent 管理

- `GET /api/agents`：读取全局内置 Agent 模板。
- `GET /api/agents/:agentId`：读取单个内置 Agent 模板。
- `GET /api/projects/:projectId/agents`：读取项目 workspace 可见 Agent。
- `POST /api/projects/:projectId/agents`：创建项目级自建 Agent。
- `PATCH /api/projects/:projectId/agents/:agentId`：编辑项目级 Agent 或内置 Agent 的工作区覆盖。
- `DELETE /api/projects/:projectId/agents/:agentId`：删除项目级自建 Agent。

注意：全局 `POST/PATCH/DELETE /api/agents` 是兼容保留路由，当前会返回 `400`，移动端不要使用。

### 文件、预览、Diff

- `GET /api/projects/:projectId/files`：文件树。
- `GET /api/projects/:projectId/files/content?path=...`：文本文件内容。
- `GET /api/projects/:projectId/files/preview?path=...`：PDF / DOCX / PPTX 预览元数据。
- `PUT /api/projects/:projectId/files`：写入 workspace 文件。
- `GET /api/projects/:projectId/diff`：当前 Git diff。
- `POST /api/projects/:projectId/change-sets/:changeSetId/apply`：应用 Runtime change set。
- `GET /api/projects/:projectId/preview-targets`：Runtime 静态预览入口。
- `GET /api/projects/:projectId/preview-capability`：检测预览模式和构建状态。
- `POST /api/projects/:projectId/preview-build?force=true`：启动或重试预览构建。

移动端第一阶段建议只做文件、预览、Diff 摘要和 WebView 入口；复杂编辑和 Monaco 仍保留 Web 端。

### 版本、构建、部署

- `GET /api/projects/:projectId/delivery`：当前交付汇总。
- `POST /api/projects/:projectId/versions`：保存当前 workspace repo 为版本。
- `GET /api/projects/:projectId/versions`：版本列表。
- `GET /api/projects/:projectId/version-diff?v1=...&v2=...`：版本 diff。
- `POST /api/projects/:projectId/versions/:versionId/restore`：恢复版本。
- `GET /api/projects/:projectId/source.zip?versionId=...`：下载源码 zip。
- `POST /api/projects/:projectId/builds`：构建指定版本。
- `POST /api/projects/:projectId/deploy`：部署构建版本到本地 latest。

移动端第一阶段可展示交付状态和触发保存/构建/部署按钮；版本 diff 详情建议先跳 Web 端或只展示摘要。

### 静态资源路由

- `/preview/runtime/:projectId/**`
- `/build-preview/:projectId/:sourceHash/**`
- `/preview/**`
- `/deploy/:projectId/latest/**`

移动端 WebView 加载这些相对 URL 时必须拼接业务后端 origin，例如 `http://120.79.130.49:8790/build-preview/...`。

## 移动端数据映射

### Workspace

`agentHubApp/src/data/mockData.ts` 中的 `Workspace` 可由 `GET /api/workbench` 的 `rooms[]` 映射：

| App 字段 | 后端来源 |
| --- | --- |
| `id` | `room.id` 或 `room.workspace.id` |
| `name` | `room.workspace.name` 或 `room.title` |
| `goal` | `room.workspace.goal` 或 `room.subtitle` |
| `kind` | `room.kind` |
| `type` | `room.workspace.workspaceType` |
| `status` | `room.workspace.runtimeStatus` 映射为 `ready/running/failed` |
| `pinned` | `Boolean(room.workspace.pinnedAt)` |
| `archived` | `Boolean(room.workspace.archivedAt)` |
| `agents` | `room.participantAgentIds` |
| `runningAgents` | `room.signal.runningAgents` |
| `artifactCount` | `room.signal.artifactCount` |
| `messageCount` | `room.signal.messageCount` |
| `latestEventLabel` | `room.signal.latestEventLabel` |
| `updatedAt` | `room.lastActivityAt` |

### Agent

App 的轻量 `Agent` 可由 `AgentDefinition` 映射：

| App 字段 | 后端来源 |
| --- | --- |
| `id` | `agent.id` |
| `name` | `agent.name` |
| `role` | `agent.role` 或 `agent.description` |
| `provider` | `agent.modelProvider` |
| `status` | 第一阶段从 `agentRuns` / `workflowEvents` 归纳；缺省 `idle` |
| `skills` | `agent.skills`，缺省空数组 |

### ChatMessage

App 的 `ChatMessage` 可由 `state.messages[]` 映射：

| App 字段 | 后端来源 |
| --- | --- |
| `id` | `message.id` |
| `sender` | `message.senderType === 'user' ? 'user' : 'agent'` |
| `agentId` | `message.senderId` |
| `text` | `message.content` |
| `time` | `message.createdAt` 格式化 |
| `quote` | `message.replyTo?.excerpt` |
| `process` | 从 `state.workflowEvents[]` 归纳 |
| `artifacts` | 从 `message.artifacts` 或 `state.artifacts[]` 归纳 |

## 接入实现路线

### 第 1 阶段：API 基础层

1. 在 `agentHubApp/src/api/businessBackend.ts` 新增移动端 API 客户端。
2. 默认 base URL 使用 `http://120.79.130.49:8790`，同时允许通过 Expo env 覆盖，例如 `EXPO_PUBLIC_BUSINESS_API_BASE_URL`。
3. 封装 `requestJson`、错误解析、`absoluteBackendUrl(path)`。
4. 优先实现这些方法：
   - `fetchHealth`
   - `fetchWorkbenchOverview`
   - `fetchProjectState`
   - `createWorkspace`
   - `updateWorkspaceMetadata`
   - `fetchProjectAgents`
   - `createProjectAgent`
   - `updateProjectAgent`
   - `deleteProjectAgent`
   - `streamProjectMessage`

### 第 2 阶段：类型和 mapper

1. 新增 `agentHubApp/src/api/types.ts` 定义后端响应最小类型。
2. 新增 `agentHubApp/src/api/mappers.ts`，把后端 `WorkbenchOverview`、`ProjectStateEnvelope` 映射到 App 当前 UI 类型。
3. 保留 `mockData.ts` 作为离线 fallback 或开发 seed，不再作为主数据源。

### 第 3 阶段：工作台接真实数据

1. `App.tsx` 首屏加载 `GET /api/workbench`。
2. 增加 `loading/error/refresh` 状态。
3. 工作区搜索从本地 Fuse 过渡为后端 `query` 参数；本地 Fuse 可作为已加载数据内的即时过滤。
4. 工作区筛选请求必须每次传入当前三个筛选栏的完整三元组：`status`、`sortBy`、`sortDirection`。不要只传发生变化的字段，也不要依赖刚刚 `setState` 后的旧值。
5. 置顶/归档调用 `PATCH /api/projects/:projectId/metadata` 后刷新 workbench。
6. 新建工作区调用 `POST /api/projects`，成功后切到新 workspace 的聊天页。

### 第 4 阶段：聊天和 SSE

1. 进入聊天页后调用 `GET /api/projects/:projectId/state?messageLimit=40`。
2. 消息列表从 `state.messages` 映射。
3. 发送消息调用 `POST /api/projects/:projectId/messages/stream`。
4. 使用 `react-native-sse` 或 fetch streaming 处理 SSE；Expo 环境优先使用项目已安装的 `react-native-sse`。
5. 收到 `assistant_delta` 时追加临时流式消息；stream 结束后刷新当前项目 state。

### 第 5 阶段：Agent 管理

1. Agent 页面读取当前项目 `GET /api/projects/:projectId/agents`。
2. 新建/编辑/删除全部走项目级 Agent 接口。
3. 内置 Agent 只开放 `name/modelProvider/model` 编辑；自建 Agent 开放完整字段。
4. 创建或删除后刷新 workbench 和当前项目 state，确保群聊成员同步。

### 第 6 阶段：产物和交付摘要

1. 当前产出卡片从 `state.artifacts`、`state.changeSets`、`GET /api/projects/:projectId/delivery` 映射。
2. 预览 URL 统一用 `absoluteBackendUrl(relativeUrl)` 拼成完整地址。
3. 可在移动端用 `react-native-webview` 打开 `/preview`、`/build-preview`、`/deploy` 链接。
4. 保存版本、构建、部署按钮分别调用 versions、builds、deploy 接口；第一阶段以状态反馈为主。

## Web 端同步调整

`agentHubFrontend` 已有 `src/api/businessBackend.ts`，但默认同源 `/api`。如果 Web 端也要直接连远端服务器，需要做其中一种：

1. 修改 `vite.config.ts` proxy 到 `http://120.79.130.49:8790`。
2. 或给 `businessBackend.ts` 增加 `VITE_BUSINESS_API_BASE_URL`，所有 fetch 统一拼 base URL。

推荐第二种，和移动端保持一致，方便本地、测试、生产环境切换。

## 风险和确认项

- 远端后端是否开启 CORS：Web 端跨域直连需要 CORS；移动端原生请求通常不受浏览器 CORS 限制。
- SSE 在 Expo Go、Android、iOS 上的兼容性要实测；必要时为移动端增加非流式降级刷新。
- `/preview`、`/build-preview`、`/deploy` 返回的是网页资源，移动端必须使用完整 URL 给 WebView。
- 当前接口文档明确“没有鉴权层”，上线前需要补 token 或网关鉴权；demo 阶段至少不要把敏感环境暴露到公网。
- `POST /api/projects/:projectId/versions/:versionId/restore` 会恢复 repo，属于高风险操作，移动端建议二次确认。

## 建议验收顺序

1. App 能显示真实工作区列表。
2. App 能创建新工作区并自动进入聊天。
3. App 能读取真实消息历史。
4. App 能发送消息并看到 SSE 流式回复。
5. App 能置顶/归档工作区。
6. App 能读取和管理项目级 Agent。
7. App 能打开真实预览链接。
8. App 能展示交付状态，并触发保存版本、构建、部署。

## 是否需要生成 Skill

本轮先不生成全局 skill。原因是当前任务的关键资产是项目内接口路线、字段映射和工程落点，放在 `docs` 下更直接。等完成第一轮接入后，如果后续会反复执行“读取接口文档 -> 生成移动端 API 客户端 -> 映射 mock UI -> 验证 SSE”的同类任务，再抽成 `agenthub-app-api-integration` skill 更合适。

## 接口字段映射复盘记录

本次工作区置顶渲染问题的根因不是接口复杂，而是前端在未核对真实响应体组合状态前，给 UI 过滤条件额外加了语义假设。

后续接入规则：

1. 列表渲染必须先以真实接口响应体为准确认字段位置，例如工作区列表来自 `GET /api/workbench` 的 `rooms[]`。
2. `pinned` 只由 `Boolean(room.workspace.pinnedAt)` 决定；`archived` 只由 `Boolean(room.workspace.archivedAt)` 决定。两者是独立状态，不能假设互斥。
3. 置顶工作区展示只判断 `pinned === true`。即使同一工作区也存在 `archivedAt`，只要有 `pinnedAt` 就应展示在置顶区，除非产品明确要求“置顶区只展示 active 置顶”。
4. 当接口 `page.total` 或 `rooms.length` 与页面渲染数量不一致时，优先检查 mapper 和 UI filter 是否额外排除了字段，不要先改缓存、分页或请求参数。
5. 调试响应体弹窗应支持复制完整 JSON，方便直接核对字段，不要凭截图或字段名猜测。
