一、总体架构

采用前后端分离架构。业务后端使用 Node.js 提供 REST API，前端使用 React 或 Vue。当前项目是 demo 阶段，服务器本地存储约 60G，暂时不接入阿里云 OSS；源码压缩包、编译产物、部署产物都存储在业务后端服务器本地磁盘，并通过后端静态资源路由提供预览、部署访问和下载能力。

版本控制继续通过 Git 实现。每个业务项目在服务器本地磁盘中独立一个 Git 仓库，版本历史通过 Git tag 管理，Diff 通过 git diff 临时计算。Git 仓库是源码历史的权威来源；源码 zip、build 目录和 deploy 目录都是围绕某个 Git 版本生成的产物。

AgentHub 只负责代码生成、代码修改、审查、自动返工和结构化交付结果，不直接负责项目 Git 版本、构建产物、预览地址、源码包和部署发布。业务后端消费 AgentHub 的已验收交付结果，然后完成项目落库、Git commit/tag、Docker 构建、本地预览和部署发布。

为避免后续切换成本，业务后端内部保留 StorageService 抽象。第一阶段实现 LocalStorageService，把文件写到本地磁盘；如果以后确实需要 OSS，只替换 StorageService 的实现，不改 AgentHub 链路和主要业务流程。

二、本地存储目录规划

建议业务后端通过环境变量配置存储根目录，例如 APP_STORAGE_ROOT。该目录应放在代码仓库之外，或至少加入 .gitignore，避免把用户项目、构建产物和临时文件提交进业务代码仓库。

推荐目录结构：

```text
{APP_STORAGE_ROOT}/
  projects/
    {projectId}/
      repo/                         # 每个项目一个独立 Git 仓库
  artifacts/
    source/
      {projectId}/{versionId}.zip   # 指定版本源码包
    build/
      {projectId}/{versionId}/      # Docker 构建产物，包含 index.html 和静态资源
  deploy/
    {projectId}/latest/             # 当前发布版本的静态站点
  tmp/
    builds/{jobId}/                 # 构建临时目录，构建结束后清理
```

60G 对 demo 足够，但需要明确清理策略：

- 不长期保存 node_modules，不把依赖目录写入 Git，也不打进源码 zip。
- tmp/builds 构建临时目录在任务结束后清理，失败任务也要有兜底清理。
- 每个项目默认保留最近 5 到 10 个 build 产物和 source zip，旧版本源码历史由 Git 仓库保留。
- deploy/{projectId}/latest 只保留当前发布版本，用户需要回滚时从指定 Git tag 重新构建或复制对应 build 产物。
- 后端所有文件读写必须做路径归一化和根目录校验，禁止通过 ../ 访问存储根目录之外的文件。

三、核心功能模块与流程

1. Agent 代码生成与初次预览

用户在前端发起生成需求，业务后端调用 AgentHub。AgentHub 完成工程师生成、交付校验、审查和必要的一次自动返工后，返回结构化交付结果，包括文件清单、变更集、预览建议和验收状态。业务后端只接收通过验收的交付结果进入正式项目版本。

业务后端执行：

- 为项目创建唯一 projectId，在 {APP_STORAGE_ROOT}/projects/{projectId}/repo 初始化 Git 仓库。
- 将 AgentHub 交付的文件写入 repo 工作区，忽略 node_modules、临时日志、系统文件等不应入库内容。
- 执行 git add、git commit，并创建版本 tag，例如 v_20260525_153000 或 v1。
- 将该版本工作区打包为 zip，保存到 artifacts/source/{projectId}/{versionId}.zip。
- 使用 Docker 构建项目，在容器中执行 npm install 和 npm run build。
- 将 dist 或 build 目录复制到 artifacts/build/{projectId}/{versionId}/。
- 返回本地预览 URL，例如 /preview/{projectId}/{versionId}/index.html。

前端将预览 URL 放入 iframe 的 src 中显示，用户可以交互。

2. 用户编辑与重新编译

用户在前端 Monaco 编辑器中修改代码，支持文件树和多文件编辑。修改完成后点击“重新编译”按钮，不做实时编译。

业务后端执行：

- 根据 projectId 找到对应 Git 仓库。
- 将前端提交的文件内容写入工作区，覆盖旧文件；第一阶段可以提交全量文件，后续再优化为增量 patch。
- 检查是否真的有文件变化；如果没有变化，不创建新 commit，只返回当前版本状态。
- 有变化时执行 git add、git commit，创建新 tag。
- 生成新版源码 zip 到 artifacts/source/{projectId}/{versionId}.zip。
- 重新执行 Docker 构建，将新构建产物写入 artifacts/build/{projectId}/{versionId}/。
- 返回新的本地预览 URL。

前端更新 iframe 的 src，刷新预览。

3. 版本历史与 Diff

前端提供版本历史入口，请求后端 /project/:id/versions 接口。后端通过 git tag --list 和 git show 获取 tag、提交时间、提交信息，返回版本列表。

用户选择两个版本后，前端请求 /project/:id/diff?v1=tag1&v2=tag2。后端执行 git diff tag1 tag2 或 git diff tag1..tag2，返回 unified diff 文本。前端使用 Monaco Diff Editor 展示差异。

Diff 不需要单独存储，按需从 Git 临时计算。

4. 对话式局部修改

用户在 Monaco 编辑器中选中一段代码，点击“在聊天中修改”，输入修改意图。前端将 projectId、当前文件路径、完整文件内容、选中片段和用户指令发送给业务后端。

建议优先复用 AgentHub 的代码修改能力：业务后端把局部修改任务交给 AgentHub，AgentHub 通过工程师 Agent 产出修改后的文件或 changeSet，并经过必要的审查。第一阶段如果要做轻量 demo，也可以由业务后端直接调用模型返回修改后的完整文件内容，但长期应收敛到 AgentHub 统一处理生成、修改、审查和返工。

模型或 Agent 返回后，后端将修改后的完整文件内容返回给前端。前端替换编辑器内容，但不自动生成新版本；用户点击“重新编译”后，才触发 Git commit、tag、build 和 preview 更新。

5. 文档与 PPT 预览

Agent 可能生成 PDF、Word、PPT 等文件。demo 阶段这些文件存储在本地 artifacts 或 deploy 目录，通过业务后端静态文件路由提供访问 URL。

前端根据文件扩展名选择预览组件：

- PDF：使用 react-pdf 或 PDF.js 嵌入。
- Word：使用 mammoth.js 转为 HTML 显示。
- PPT：优先使用本地可渲染方案，例如 pptxviewjs 转 Canvas；Office Online Viewer 需要公网 URL，本地 demo 阶段不作为首选。

所有文档卡片支持全屏预览。后端返回的文档 URL 需要带项目和版本标识，便于权限校验和版本追踪。

6. 部署发布

用户点击“部署”按钮，前端请求后端 /deploy 接口。后端将当前最新版本或用户指定版本的构建产物从 artifacts/build/{projectId}/{versionId}/ 复制到 deploy/{projectId}/latest/。

后端通过静态路由返回永久访问地址，例如 /deploy/{projectId}/index.html。这里的“永久”只表示 demo 服务器本地稳定地址，不等同于公网高可用发布。

源码下载通过后端接口直接读取本地 zip 并 stream 返回，例如：

```text
GET /api/projects/{projectId}/versions/{versionId}/source.zip
```

不需要 OSS 签名 URL。

四、技术栈详细清单

后端：

- Node.js 18+
- Express 或 Fastify 框架
- simple-git：封装 Git 命令行操作，用于 commit、tag、版本历史和 diff
- archiver：打包 zip 源码文件
- fs-extra 或 Node.js fs/promises：本地文件复制、清理和目录管理
- dockerode 或 child_process：管理 Docker 构建任务
- bull 队列或轻量内存队列：处理构建任务，避免阻塞主线程；demo 初期可先同步执行，后续再队列化
- 可选数据库：SQLite 或 PostgreSQL，用于存储项目元数据、版本记录、构建状态和本地路径映射；demo 初期也可以用 Git + 文件系统 + JSON 元数据起步

前端：

- React 18+ 或 Vue 3
- Monaco Editor：核心代码编辑器，支持多文件、语法高亮和 Diff 模式
- 组件库：Ant Design 或 Element Plus，用于快速搭建按钮、列表、弹窗和状态展示
- iframe：预览容器，必须设置 sandbox 属性，例如 allow-scripts allow-same-origin allow-popups allow-forms，但不能 allow-top-navigation
- react-pdf、mammoth.js、pptxviewjs：文档预览库
- axios 或 fetch：调用后端 API

构建与隔离：

- Docker：为每个构建任务启动独立容器，容器内预装 Node.js，动态执行 npm install 和 npm run build。
- 资源限制：demo 阶段建议 CPU 1 核、内存 2GB、超时 5 分钟。
- 基础镜像：node:18-alpine 或 node:20-alpine，并根据需要预装常见 CLI，例如 vite、@angular/cli、vue-cli。
- 构建网络：允许访问 npm registry 或指定镜像源，禁止访问内网服务。
- 依赖缓存：demo 阶段可先不缓存 node_modules；如果构建太慢，再考虑 pnpm store 或 Docker volume 缓存，但要保持项目隔离。

本地存储服务：

- LocalStorageService 负责源码 zip、build 产物、deploy 产物、临时目录和静态访问路径。
- 对外只暴露 saveSourceZip、saveBuildArtifact、publishDeploy、openSourceZipStream、getPreviewUrl、getDeployUrl、cleanupOldArtifacts 等能力。
- 业务流程依赖 StorageService 接口，不直接散落操作本地路径；以后迁移 OSS 时替换实现即可。

五、关键决策与注意事项

- demo 阶段不使用 OSS。60G 本地磁盘足够支撑小规模项目预览、版本历史和构建产物保存。
- Git 仓库存储在业务后端服务器本地持久化目录，每个项目一个仓库。
- Git 是源码历史的权威来源；source zip、build 产物和 deploy 目录是可重新生成的产物。
- 每次成功重新编译才产生新版本；没有文件变化时不创建 commit。
- 编译不在前端完成，也不在用户输入时实时执行，只在用户点击“重新编译”或“部署”相关操作后触发。
- AgentHub 不负责业务项目的版本管理和部署存储。AgentHub 负责交付代码能力，业务后端负责把通过验收的代码变成项目版本。
- 预览、部署和下载都走业务后端路由，第一阶段不依赖公网 URL。
- 本地静态路由必须做好权限校验和路径安全，不能直接暴露任意磁盘目录。
- 对话式修改应尽量复用 AgentHub 的生成、审查和返工能力，避免业务后端另起一套不可审查的模型链路。
- 后续如果要大规模上线，再把 LocalStorageService 替换为 OSSStorageService，并补充 CDN、签名 URL、生命周期规则和对象权限控制。

六、开发顺序建议（共 7-9 天）

1. 搭建业务后端基础框架，实现 LocalStorageService、项目创建、本地目录初始化和 Git 仓库初始化。
2. 接入 AgentHub 的已验收交付结果，实现“AgentHub 交付文件 -> 写入项目 repo -> commit/tag”的闭环。
3. 实现源码 zip 打包和本地下载接口。
4. 实现 Docker 构建，将 dist/build 产物保存到 artifacts/build，并返回 /preview/{projectId}/{versionId}/index.html。
5. 实现前端预览卡片和 iframe 渲染，完成“Agent 生成 -> Git 版本 -> Docker 构建 -> 本地预览”的基础流程。
6. 集成 Monaco 编辑器，实现文件树、多文件编辑和“重新编译”按钮。
7. 实现版本历史列表和 Diff 视图，后端通过 Git tag 和 git diff 提供数据。
8. 实现文档预览组件，包括 PDF、Word、PPT 的本地 URL 预览。
9. 实现对话式局部修改、部署发布和旧产物清理策略。

如果时间紧，第一阶段优先完成 1 到 7，文档预览、对话式局部修改和部署发布可以作为第二阶段。

七、与比赛要求的对应关系

- 内联产物预览卡片：网页 iframe、PDF/Word/PPT 文档渲染，通过本地静态路由和前端预览组件实现。
- 点击卡片展开全屏预览/代码编辑器：通过 Monaco 编辑器和全屏预览面板实现。
- 支持 Diff 视图、版本历史、对话式局部修改：通过 Git 版本管理、Monaco Diff Editor 和 AgentHub 修改能力实现。
- 部署发布：通过本地 deploy/{projectId}/latest 静态站点发布和源码 zip 下载实现。

本方案基于前后端 + 本地磁盘 + Git + Docker + AgentHub。OSS 不再作为 demo 阶段依赖。AgentHub 只负责生成、修改、审查和返工代码；业务后端负责项目版本、构建、预览、下载和部署。所有核心需求仍有明确实现路径，并保留以后迁移到 OSS 的接口边界。
