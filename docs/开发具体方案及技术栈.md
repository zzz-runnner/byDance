一、总体架构

采用前后端分离架构。Agent 能力、业务后端、前端继续保持边界清晰：

- AgentHub：负责主脑调度、真实子 Agent 执行、代码生成/修改、审查、交付校验、一次自动返工、changeSet、原始 workspace 预览和源码 zip。
- 业务后端：负责业务项目元数据、版本记录、把已验收的 AgentHub workspace 固化为产品版本、Docker 构建、本地构建产物预览、源码下载和部署发布。
- 前端：负责聊天工作台、项目预览、Monaco 编辑、版本历史、Diff 和发布操作。

当前项目是 demo 阶段，服务器本地存储约 60G，暂时不接入阿里云 OSS。源码快照、构建产物和部署产物都先存储在服务器本地磁盘，并通过后端静态资源路由提供访问能力。

这里要特别区分两类“本地文件夹”：

- AgentHub runtime workspace：真实 engineer/Codex 子 Agent 直接写文件的位置。当前路径形态是 `data/workspaces/{workspaceId}/repo`，每个 workspace 会初始化为独立 Git repo，并由 AgentHub 生成 changeSet、`/preview/{workspaceId}` 和 `/api/workspaces/{workspaceId}/zip`。
- 业务后端 storage：业务产品版本、构建产物、发布产物和元数据的位置。业务后端不应该把 Agent 输出文本重新解析成文件再写一次；它应该在 AgentHub 验收通过后，基于现成的 workspace repo 做版本固化和构建。

因此，第一阶段建议把 `workspaceId` 和 `projectId` 建立一对一绑定：一个业务项目对应一个 AgentHub workspace，Agent 生成和后续 Agent 修改都直接落在这个 workspace repo 里。业务后端只在“验收通过、用户接受、需要生成产品版本”时，对这个已有 repo 做 commit/tag/build/deploy。

为避免后续切换成本，业务后端内部仍保留 `StorageService` 抽象。第一阶段实现 `LocalStorageService`，把源码快照、构建产物和发布产物写到本地磁盘；以后确实需要 OSS 时，只替换存储实现，不改 AgentHub 主链路。

二、本地存储目录规划

1. AgentHub runtime 目录

AgentHub 已经有自己的 workspace runtime 根目录，默认类似：

```text
agentHub/
  data/
    workspaces/
      {workspaceId}/
        repo/                       # 真实子 Agent 写文件的位置，也是独立 Git repo
```

这个目录由 AgentHub 管理。业务后端可以通过 AgentHub API、workspaceId、zip 接口或受控的本机路径配置引用它，但不应该绕开边界随意扫描整个 `data/workspaces`。

2. 业务后端 storage 目录

建议业务后端通过环境变量配置存储根目录，例如 `APP_STORAGE_ROOT`。该目录放在业务后端代码仓库之外，或至少加入 `.gitignore`。

推荐结构：

```text
{APP_STORAGE_ROOT}/
  projects/
    {projectId}/
      metadata.json                 # projectId、workspaceId、当前版本、创建时间等元数据
  artifacts/
    source/
      {projectId}/{versionId}.zip   # 从 AgentHub workspace repo 生成的源码快照
    build/
      {projectId}/{versionId}/      # Docker 构建产物，包含 index.html 和静态资源
  deploy/
    {projectId}/latest/             # 当前发布版本的静态站点
  tmp/
    builds/{jobId}/                 # 构建临时目录，构建结束后清理
```

第一阶段不建议再给业务后端创建第二份 `{projectId}/repo`。否则 AgentHub workspace repo 和业务后端 project repo 会出现双源头，后续同步、Diff 和返工都会变复杂。

60G 对 demo 足够，但需要明确清理策略：

- 不长期保存 `node_modules`，不把依赖目录写入 Git，也不打进源码 zip。
- `tmp/builds` 构建临时目录在任务结束后清理，失败任务也要兜底清理。
- 每个项目默认保留最近 5 到 10 个 build 产物和 source zip。
- AgentHub workspace repo 保留源码工作区和 Git 历史；业务后端 source zip/build/deploy 都是围绕某个版本生成的产物。
- 所有文件读写必须做路径归一化和根目录校验，禁止通过 `../` 访问根目录之外的文件。

三、核心功能模块与流程

1. Agent 代码生成与初次预览

用户在前端发起生成需求，业务后端创建或选择一个业务项目，并绑定一个 AgentHub workspace。之后由 AgentHub 负责真实生成链路：

- AgentHub 准备 `data/workspaces/{workspaceId}/repo`。
- 工程师 Agent 直接在该 repo 中创建或修改文件。
- AgentHub 读取 repo diff，生成 changeSet。
- AgentHub 执行交付校验、Reviewer 审查和必要的一次自动返工。
- 验收通过后，AgentHub 产生 `preview_ready`、`change_set_created`、`workflow_finished` 等事件。
- 原始预览可以直接使用 AgentHub 的 `/preview/{workspaceId}`。
- 源码 zip 可以直接使用 AgentHub 的 `/api/workspaces/{workspaceId}/zip`，该 zip 来自 workspace repo 当前内容。

业务后端在这一步不重新写 Agent 交付文件。它只需要记录：

- `projectId`
- `workspaceId`
- 最新 changeSet id
- AgentRun / workflow 状态
- 原始 workspace 预览 URL
- 是否已被用户接受为产品版本

当用户点击“保存版本”或“生成预览构建”时，业务后端再对现有 workspace repo 执行产品版本固化：

- 检查 AgentHub 交付状态必须通过：engineer 成功、delivery validation 通过、reviewer PASS、没有 `repair_blocked`。
- 检查 workspace repo 是否有文件变化。
- 如果有变化，对该 repo 执行产品版本 commit，并创建 tag，例如 `v_20260525_153000` 或 `v1`。
- 从该 repo 生成源码 zip，保存到 `artifacts/source/{projectId}/{versionId}.zip`。
- 使用 Docker 从该 repo 构建项目。
- 将 `dist` 或 `build` 目录复制到 `artifacts/build/{projectId}/{versionId}/`。
- 返回业务构建预览 URL，例如 `/build-preview/{projectId}/{versionId}/index.html`。

注意：AgentHub 的 `/preview/{workspaceId}` 是 workspace 原始文件预览；业务后端的 `/build-preview/{projectId}/{versionId}` 是 Docker 构建后的产品预览。两者不要混用。

2. 用户编辑与重新编译

用户在前端 Monaco 编辑器中修改代码，支持文件树和多文件编辑。修改完成后点击“重新编译”按钮，不做实时编译。

这里的手动编辑不是 Agent 交付。业务后端可以把用户提交的文件内容写回同一个 AgentHub workspace repo，或者通过一个受控的源码服务接口写入。关键是仍然保持单一源码工作区，不再创建第二份 project repo。

重新编译流程：

- 根据 `projectId` 找到绑定的 `workspaceId`。
- 定位 `data/workspaces/{workspaceId}/repo` 或调用 AgentHub 提供的受控文件接口。
- 将用户编辑后的文件写入同一个 workspace repo。
- 检查是否真的有文件变化；没有变化时不创建新版本。
- 有变化时执行产品版本 commit/tag。
- 生成新版源码 zip 到 `artifacts/source/{projectId}/{versionId}.zip`。
- 重新执行 Docker 构建，将新构建产物写入 `artifacts/build/{projectId}/{versionId}/`。
- 返回新的业务构建预览 URL。

前端更新 iframe 的 src，刷新预览。

3. 版本历史与 Diff

前端提供版本历史入口，请求后端 `/project/:id/versions` 接口。业务后端通过绑定 workspace repo 的 Git tag 获取版本列表，也可以结合数据库中的版本元数据返回构建状态、预览地址和创建时间。

用户选择两个版本后，前端请求 `/project/:id/diff?v1=tag1&v2=tag2`。业务后端在绑定的 workspace repo 中执行 `git diff tag1 tag2` 或 `git diff tag1..tag2`，返回 unified diff 文本。前端使用 Monaco Diff Editor 展示差异。

Diff 不需要单独存储，按需从 Git 临时计算。

4. 对话式局部修改

用户在 Monaco 编辑器中选中一段代码，点击“在聊天中修改”，输入修改意图。前端将 `projectId`、当前文件路径、完整文件内容、选中片段和用户指令发送给业务后端。

推荐做法是复用 AgentHub，而不是业务后端单独调用模型：

- 业务后端根据 `projectId` 找到 `workspaceId`。
- 将局部修改任务发送给 AgentHub 的对应 workspace。
- 工程师 Agent 直接在 `data/workspaces/{workspaceId}/repo` 修改文件。
- AgentHub 继续产生 changeSet、交付校验、Reviewer 审查和必要的一次返工。
- 前端根据 AgentHub 事件刷新文件树、原始预览和聊天状态。

用户确认后，再由业务后端执行产品版本 commit/tag 和 Docker 构建。这样对话式修改、审查、返工和版本固化都走同一条链路。

5. 文档与 PPT 预览

Agent 可能生成 PDF、Word、PPT 等文件。文件首先仍然落在 AgentHub workspace repo 中。AgentHub 的 zip 和 preview 可以暴露这些文件的原始访问能力；业务后端在产品版本固化时，把这些文件纳入源码快照或构建产物。

前端根据文件扩展名选择预览组件：

- PDF：使用 `react-pdf` 或 PDF.js 嵌入。
- Word：使用 `mammoth.js` 转为 HTML 显示。
- PPT：优先使用本地可渲染方案，例如 `pptxviewjs` 转 Canvas；Office Online Viewer 需要公网 URL，本地 demo 阶段不作为首选。

所有文档卡片支持全屏预览。后端返回的文档 URL 需要带 projectId/workspaceId/versionId，便于权限校验和版本追踪。

6. 部署发布

用户点击“部署”按钮，前端请求业务后端 `/deploy` 接口。业务后端将当前最新版本或用户指定版本的构建产物从 `artifacts/build/{projectId}/{versionId}/` 复制到 `deploy/{projectId}/latest/`。

后端通过静态路由返回访问地址，例如 `/deploy/{projectId}/index.html`。这里的“永久”只表示 demo 服务器本地稳定地址，不等同于公网高可用发布。

源码下载有两种来源：

- 未固化版本：直接使用 AgentHub `/api/workspaces/{workspaceId}/zip`。
- 已固化版本：由业务后端读取 `artifacts/source/{projectId}/{versionId}.zip` 并 stream 返回。

demo 阶段不需要 OSS 签名 URL。

四、技术栈详细清单

后端：

- Node.js 18+
- Express 或 Fastify 框架
- simple-git：封装 Git 命令行操作，用于产品版本 commit、tag、版本历史和 diff
- archiver 或 fflate：打包源码 zip
- fs-extra 或 Node.js fs/promises：本地文件复制、清理和目录管理
- dockerode 或 child_process：管理 Docker 构建任务
- bull 队列或轻量内存队列：处理构建任务，避免阻塞主线程；demo 初期可先同步执行，后续再队列化
- 可选数据库：SQLite 或 PostgreSQL，用于存储 projectId、workspaceId、版本记录、构建状态、本地路径映射和部署记录

AgentHub 对接：

- `POST /api/workspaces`：创建 AgentHub workspace。
- `POST /api/messages/stream`：发送用户任务并消费 workflow events。
- `/preview/{workspaceId}`：查看 AgentHub workspace 原始预览。
- `/api/workspaces/{workspaceId}/zip`：下载当前 workspace repo 的源码 zip。
- workflow events：重点消费 `task_stage_updated`、`agent_task_dispatched`、`change_set_created`、`delivery_validation_finished`、`review_verdict`、`repair_started`、`repair_finished`、`repair_blocked`、`preview_ready`、`zip_ready`、`workflow_finished`。

前端：

- React 18+ 或 Vue 3
- Monaco Editor：核心代码编辑器，支持多文件、语法高亮和 Diff 模式
- 组件库：Ant Design 或 Element Plus，用于快速搭建按钮、列表、弹窗和状态展示
- iframe：预览容器，必须设置 sandbox 属性，例如 `allow-scripts allow-same-origin allow-popups allow-forms`，但不能 `allow-top-navigation`
- react-pdf、mammoth.js、pptxviewjs：文档预览库
- axios 或 fetch：调用后端 API 和消费 SSE

构建与隔离：

- Docker：为每个构建任务启动独立容器，容器内预装 Node.js，动态执行 `npm install` 和 `npm run build`。
- 资源限制：demo 阶段建议 CPU 1 核、内存 2GB、超时 5 分钟。
- 基础镜像：`node:18-alpine` 或 `node:20-alpine`，并根据需要预装常见 CLI，例如 vite、@angular/cli、vue-cli。
- 构建网络：允许访问 npm registry 或指定镜像源，禁止访问内网服务。
- 依赖缓存：demo 阶段可先不缓存 `node_modules`；如果构建太慢，再考虑 pnpm store 或 Docker volume 缓存，但要保持项目隔离。

本地存储服务：

- `LocalStorageService` 负责业务源码快照、build 产物、deploy 产物、临时目录和静态访问路径。
- 对外只暴露 `saveSourceZip`、`saveBuildArtifact`、`publishDeploy`、`openSourceZipStream`、`getBuildPreviewUrl`、`getDeployUrl`、`cleanupOldArtifacts` 等能力。
- 业务流程依赖 `StorageService` 接口，不直接散落操作本地路径；以后迁移 OSS 时替换实现即可。

五、关键决策与注意事项

- demo 阶段不使用 OSS。60G 本地磁盘足够支撑小规模项目预览、版本历史和构建产物保存。
- AgentHub 子 Agent 已经直接把代码写入本地 workspace repo；业务后端不要再把 Agent 文本输出当成文件映射重新写一遍。
- 第一阶段推荐 `projectId` 绑定 `workspaceId`，复用 AgentHub workspace repo 作为项目源码工作区。
- 业务后端负责“产品版本固化”：在验收通过后，对现有 workspace repo 执行 commit/tag、源码快照、Docker 构建和部署发布。
- Git 是产品版本历史的权威来源；source zip、build 产物和 deploy 目录是可重新生成的产物。
- 每次成功重新编译或用户接受 Agent 修改后，才产生新产品版本；没有文件变化时不创建 commit。
- AgentHub 原始预览和业务构建预览要分开：`/preview/{workspaceId}` 表示当前 workspace 文件，`/build-preview/{projectId}/{versionId}` 表示构建后的版本产物。
- 编译不在前端完成，也不在用户输入时实时执行，只在用户点击“重新编译”“保存版本”或“部署”相关操作后触发。
- 本地静态路由必须做好权限校验和路径安全，不能直接暴露任意磁盘目录。
- 对话式修改应复用 AgentHub 的生成、审查和返工能力，避免业务后端另起一套不可审查的模型链路。
- 后续如果要大规模上线，再把 `LocalStorageService` 替换为 OSS 实现，并补充 CDN、签名 URL、生命周期规则和对象权限控制。

六、开发顺序建议（共 7-9 天）

1. 搭建业务后端基础框架，实现项目元数据、`projectId -> workspaceId` 绑定和 `LocalStorageService`。
2. 接入 AgentHub workspace 创建与 SSE 事件消费，跑通“用户需求 -> AgentHub workspace repo 真实落地文件 -> changeSet/review/preview”的链路。
3. 实现“验收通过后保存产品版本”：对现有 workspace repo 执行 commit/tag，并记录版本元数据。
4. 实现源码 zip 快照和本地下载接口；未固化版本可直接代理 AgentHub zip。
5. 实现 Docker 构建，将 `dist`/`build` 产物保存到 `artifacts/build`，并返回 `/build-preview/{projectId}/{versionId}/index.html`。
6. 实现前端预览卡片和 iframe 渲染，同时区分 AgentHub 原始预览和业务构建预览。
7. 集成 Monaco 编辑器，实现文件树、多文件编辑和“重新编译”按钮，修改仍写入绑定的 workspace repo。
8. 实现版本历史列表和 Diff 视图，后端通过绑定 repo 的 Git tag 和 git diff 提供数据。
9. 实现文档预览、对话式局部修改、部署发布和旧产物清理策略。

如果时间紧，第一阶段优先完成 1 到 8，文档预览、对话式局部修改和部署发布可以作为第二阶段。

七、与比赛要求的对应关系

- 内联产物预览卡片：AgentHub 原始 workspace 预览、业务构建预览、PDF/Word/PPT 文档渲染共同实现。
- 点击卡片展开全屏预览/代码编辑器：通过 Monaco 编辑器和全屏预览面板实现。
- 支持 Diff 视图、版本历史、对话式局部修改：通过绑定 workspace repo 的 Git 版本管理、Monaco Diff Editor 和 AgentHub 修改能力实现。
- 部署发布：通过本地 `deploy/{projectId}/latest` 静态站点发布和源码 zip 下载实现。

本方案基于前后端 + AgentHub workspace repo + 本地磁盘 + Git + Docker。OSS 不再作为 demo 阶段依赖。AgentHub 负责把真实代码文件直接落在本地 workspace repo，并完成生成、修改、审查、交付校验和返工；业务后端负责把已验收的 workspace 状态固化为产品版本，并处理构建、预览、下载和部署。所有核心需求仍有明确实现路径，并保留以后迁移到 OSS 的接口边界。
